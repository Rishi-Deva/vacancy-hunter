# CLAUDE.md — постоянные правила проекта AI Vacancy Hunter

## Источник правды

- Документы в `docs/` — источник правды. Архитектурные решения не пересматриваются.
- Существующие документы в `docs/` не изменять без прямого указания владельца.

Порядок чтения документов:

1. `docs/ARCHITECTURE.md`
2. `docs/TECHNICAL_SPEC.md`
3. `docs/DATABASE_SCHEMA.md`
4. `docs/SOURCES.md`
5. `docs/AGENT_PROMPTS.md`
6. `docs/IMPLEMENTATION_PLAN.md`
7. `docs/TEST_PLAN.md`

## Порядок работы

Правила владельца от 13.11.2026:

- Этапы из `IMPLEMENTATION_PLAN.md` выполняются по порядку, подряд, без ожидания слова «согласовано». Перед этапом — короткий план, затем сразу работа.
- Мелкие технические решения выбираются самостоятельно, по документации и здравому смыслу. Что выбрано и почему — кратко записывается в отчёт этапа.
- Остановиться и спросить владельца можно только в трёх случаях:
  1. нужен секрет (токен, ключ, пароль);
  2. действие необратимо (удаление данных, томов Docker, файлов);
  3. настоящее противоречие в документации, которое нельзя решить разумным выбором.
- После каждого этапа — один короткий отчёт: что сделано, результаты проверок, критерии завершения (строка «Готово, когда»).
- Каждый этап заканчивается работающим состоянием и отдельным коммитом в ветке `master`. Удалённый репозиторий не подключать без указания владельца.
- Тесты этапа пишутся в том же этапе (`TEST_PLAN.md`, раздел 4).
- Тесты нельзя отключать, пропускать или удалять, чтобы они прошли. Падающий тест — повод найти причину.

## Безопасность и изоляция

- Секреты (токены, ключи, пароли) хранятся только в `.env`. Они не попадают в код, репозиторий, логи и чат. В репозитории — только `.env.example` без значений.
- Соседний проект на том же сервере не читать, не изменять и не подключать: ни код, ни базу, ни токен, ни сессию, ни службу.
- Недоступная внешняя зависимость не блокирует шаг: источник или функция отключается в конфигурации, если это предусмотрено документацией.

## Общение с владельцем

- Объяснять действия коротко и понятно: что сделано, зачем и как проверить.
- Перед командой, которая что-то меняет или удаляет, коротко объяснять, что она делает.

## Принятые имена

- Контейнеры Docker Compose: `app`, `db`.
- Пакеты Python: `hunter_core` (общая основа), `vacancy_hunter` (логика вакансий).
- Каталоги: `config/`, `docs/`, `migrations/`, `src/`, `tests/`.
- `vacancy_hunter` может импортировать `hunter_core`, обратное запрещено.

## Команды

Служебные команды приложения: `docker compose exec app python -m vacancy_hunter <команда>` (перечень — `IMPLEMENTATION_PLAN.md`, раздел 1.2).

Запуск тестов (все модульные и интеграционные, в контейнере):

```
docker compose exec app pytest
```

Миграции применяет только одноразовый сервис `migrate` (`docker compose up -d --build` запускает его сам перед `app`; вручную — `docker compose run --rm migrate`). Данные администратора и пользователя миграций в окружение `app` не передаются.
