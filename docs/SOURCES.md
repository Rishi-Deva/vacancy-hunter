# SOURCES.md — источники вакансий AI Vacancy Hunter

Версия 1.6 от 12.11.2026. Статус: готов к реализации. Сведения о внешних сервисах с пометками «по сообщениям» и «не проверено» подтверждаются командой проверки источников на шаге A3.
Опирается на ARCHITECTURE.md (раздел 6 «Источники данных»). Сведения о внешних сервисах собраны по открытым публикациям на 12.11.2026.

Обозначения достоверности в документе:

- **подтверждено** — есть прямое свидетельство (официальная страница или аудит владельца);
- **по сообщениям** — известно из публикаций третьих лиц, нужна проверка;
- **не проверено** — данных нет, выясняется на шаге A3.

## 1. Правила доступа

| № | Правило |
|---|---------|
| R1 | Разрешены только официальные API, RSS и публичные страницы, доступные без входа |
| R2 | Запрещены обход авторизации и капчи, подмена отпечатка браузера, прокси для сокрытия источника запросов |
| R3 | Разбор HTML-страниц сайтов вакансий не применяется. Исключение — публичные страницы каналов t.me/s (решение D6) |
| R4 | Каждый запрос идёт с честным заголовком: название приложения и контакт владельца |
| R5 | Для каждого домена задана минимальная пауза между запросами. Источник не опрашивается чаще, чем раз в 3 часа |
| R6 | Источник, приславший явный запрет (403, требование входа, капча), отключается до решения владельца. Автоматических попыток обойти запрет нет |
| R7 | Соседний проект на том же сервере не затрагивается: его код, база, токен бота, сессия Telegram и служба не читаются и не изменяются |
| R8 | У AI Vacancy Hunter собственные база, бот и токен. Аккаунт Telegram для чтения каналов не используется |

Что переносится из соседнего проекта: список каналов с оценками качества (раздел 4), принципы анализатора, дедупликации и проверки свежести. Переносятся идеи и копии логики, а не общий код или общие данные.

### 2.1. Типы предложений

Система собирает три типа предложений: «Работа», «Стажировка» и «Разовый проект / фриланс» (оплачиваемые проектные задания, фриланс-заказы, технические задачи). Тип определяется при извлечении фактов и хранится у каждой записи. Источник не привязан к одному типу: в одном канале могут встречаться все три. Разовые проекты не отсеиваются из-за отсутствия трудоустройства в штат. Статистика источников и отчётов ведётся раздельно по типам.

### 4.2. Ограничения и риски

| Риск | Последствие | Мера |
|------|-------------|------|
| Владелец канала отключил предпросмотр | Страница пустая | Источник помечается недоступным, владелец получает оповещение |
| Telegram изменил разметку страницы | Разбор возвращает ноль постов | Правило: ноль постов при ранее активном канале считается сбоем, а не «нет новых» |
| Пост — реклама, резюме, курс, подборка из нескольких вакансий | Мусор в базе | Правила до LLM и поле «это вакансия» в извлечении |
| Пост пересказывает вакансию с сайта | Дубль | Ссылка из поста приводится к каноническому виду и участвует в дедупликации |
| Пост отредактирован или удалён | Устаревшие данные | Проверка актуальности перед отчётом повторно запрашивает пост. Способ уточняется на шаге A3 |
| Ограничение частоты со стороны Telegram | Ошибки 429 | Пауза и повтор по правилам ARCHITECTURE.md, раздел 16 |
| Старые посты тратят бюджет LLM | Лишние расходы | Свежесть проверяется на этапе сбора: посты старше 14 дней не сохраняются для анализа |

### 4.4. Тихий сбор и условия включения

В тихом режиме канал собирается и оценивается как обычный, но его вакансии не попадают в ежедневный отчёт и не учитываются в его статистике.

| Параметр | Значение |
|----------|----------|
| Срок наблюдения | 14 дней |
| Минимум публикаций | 10 за период. Если меньше, наблюдение продлевается ещё на 14 дней, не более двух раз |
| Порог включения | Не менее трети публикаций — реальные IT-вакансии |
| Что считается реальной IT-вакансией | Пост прошёл правила и извлечение с признаком «это предложение работы» (вакансия, стажировка или разовый заказ) и направлением «основное» или «смежное» (TECHNICAL_SPEC.md, раздел 11.4). Направление «прочее» не учитывается. Жёсткие фильтры профиля при этом не учитываются: оценивается канал, а не соответствие кандидату |
| Ограничение расходов | Через LLM проходит не более 30 постов канала за период. Остальные учитываются только по правилам. На тихий сбор всех каналов отводится не более $0,50 в месяц (значение задаётся в `llm.yaml`) |
| Решение | По итогам периода владелец получает сводку. Канал включается автоматически при выполнении условий, владелец может отменить |
| Отказ | Канал, не прошедший порог, отключается. Повторная проверка — только по команде владельца |

Статистика, которая хранится по каждому каналу: общее число публикаций, число реальных IT-вакансий, процент релевантности, число вакансий, прошедших фильтры профиля, дата начала наблюдения, дата последней проверки, текущий режим. Поля описываются в DATABASE_SCHEMA.md.

### 4.5. Пересмотр активных каналов

Раз в 30 дней статистика пересчитывается для всех активных каналов.

| Условие за последние 30 дней | Действие |
|------------------------------|----------|
| Нет ни одной вакансии | Канал временно отключается от отчёта и отправляется на повторную проверку |
| Релевантность ниже 20 % | То же |
| Условия не нарушены | Канал остаётся активным |

Повторная проверка — это тихий сбор на общих условиях раздела 4.4. Канал не удаляется: его запись, курсор и накопленная статистика сохраняются. Владелец получает оповещение при отключении и при возвращении канала в отчёт. Канал, дважды подряд не прошедший повторную проверку, остаётся отключённым до команды владельца.

## 5. Сайты вакансий

### 5.1. hh.ru и hh.kz через RSS

| Параметр | Значение |
|----------|----------|
| Состояние API | Анонимный доступ к поиску и карточкам вакансий закрыт с апреля 2026 года, запросы возвращают 403 (по сообщениям, август 2026) |
| RSS | Лента результатов поиска на сайте, параметры совпадают с параметрами поиска (по сообщениям, работала в октябре 2026) |
| Поля ленты | Название, ссылка, дата создания, компания, регион, зарплата |
| Чего нет | Полного описания, требований, формата работы |
| hh.kz | Наличие такой же ленты не проверено |

Главное ограничение: без описания невозможно извлечение фактов. Страницы вакансий по правилу R3 не разбираются. Поэтому до получения токена вакансии hh обрабатываются в **ограниченном режиме** (согласовано владельцем 12.11.2026):

| Правило | Значение |
|---------|----------|
| LLM | Не вызывается |
| Отсев | Правилами по названию и полям ленты |
| Что оценивается | Только направление и уровень по названию. Остальные критерии считаются неизвестными |
| Вид оценки | Предварительная. Хранится и считается отдельно от обычного скоринга |
| Верхняя граница | 69 баллов |
| Место в отчёте | Отдельный блок «Только по заголовку», после основных карточек |
| Лимит | Не более 5 вакансий в день |
| Слова уровня в названии | Вакансии с Senior, Lead и подобными обозначениями в блоке не показываются и не отклоняются. Они получают статус `awaiting_description` и ждут полной проверки |
| Обязательная пометка | В каждой карточке: «Оценка только по заголовку, полное описание не проверено» |

Предварительная оценка не смешивается с обычной:

- такие вакансии не участвуют в общей сортировке и не занимают места среди 15 основных карточек;
- в статистике (/stats, сводка отчёта, калибровка правил) они считаются отдельной строкой;
- категории «отличное» и «хорошее соответствие» им не присваиваются.

После получения токена ограниченный режим отключается. Вакансии hh, уже показанные по заголовку и ещё открытые, а также вакансии со статусом `awaiting_description` дозагружаются и проходят полный анализ. Описание записывается в существующую запись вакансии, дубль не создаётся. При неудаче запроса статус сохраняется, причина фиксируется, попытка повторяется позже. Вакансия, уже показанная по заголовку, в ежедневный отчёт не возвращается при любом балле. По завершении дооценки владелец получает одно уведомление: «Дооценено N вакансий, из них M получили 70 и более баллов» с кнопкой «Показать», которая открывает список с полными оценками. Вакансии, не показанные ни разу, входят в основной блок на общих основаниях по правилу первого показа (TECHNICAL_SPEC.md, раздел 14.2).

#### Подготовка заявки на приложение

Точный состав формы на портале разработчиков не проверен и мог измениться. Ниже — что подготовить заранее и как действовать.

Что подготовить:

| Пункт | Содержание |
|-------|-----------|
| Аккаунт | Действующий аккаунт на hh.ru, с которого подаётся заявка |
| Название приложения | Нейтральное, без слов «HeadHunter» и «hh» и без логотипов сервиса |
| Описание назначения | Личный инструмент соискателя: поиск вакансий по собственным критериям и уведомления себе в Telegram. Один пользователь |
| Какие методы нужны | Поиск вакансий и просмотр вакансии. Доступ к резюме, откликам и данным других пользователей не запрашивается |
| Чего приложение не делает | Не откликается автоматически, не публикует и не перепродаёт данные, не собирает базу вакансий для третьих лиц |
| Объём запросов | Несколько поисковых запросов раз в 3 часа и просмотр отобранных вакансий, порядка сотен запросов в сутки |
| Контакт | Рабочая почта владельца. Она же будет в заголовке каждого запроса |
| Адрес перенаправления | Если поле обязательно, указать любой собственный адрес. Вход пользователей через приложение не используется |

Порядок действий:

1. Прочитать действующие условия использования API на портале разработчиков. Убедиться, что личное использование соискателем не запрещено.
2. Войти на портал разработчиков hh под своим аккаунтом и открыть форму нового приложения.
3. Если форма требует выбрать тип заявителя, выбирать тот, что соответствует действительности. Не указывать статус работодателя, которого нет.
4. Заполнить форму по таблице выше. Описание писать прямо и коротко.
5. Сохранить текст заявки и дату подачи.
6. Дождаться письма о решении. По сообщениям пользователей срок от 4 дней до 2 недель.
7. При одобрении сохранить идентификатор и секрет приложения только в файле секретов на сервере. В переписку и репозиторий не отправлять.
8. При отказе запросить причину через поддержку API. Система продолжает работать в ограниченном режиме через RSS.

Риск: по сообщениям 2026 года, доступ к поиску вакансий выдаётся преимущественно работодателям и рекрутинговым сервисам. Отказ соискателю возможен. Архитектура от одобрения не зависит.

## 6. Поисковые запросы

Для Telegram-каналов запросов нет: читаются все новые посты. Для сайтов с поиском запросы задаются в конфигурации, а не в коде.

| Группа | Ключевые слова | Направление профиля |
|--------|----------------|---------------------|
| Python | python разработчик, python developer, backend python, fastapi | Python-разработка, backend |
| Боты и автоматизация | telegram бот, aiogram, автоматизация процессов, интеграции API | Боты, интеграции |
| AI | ai автоматизация, llm, ai интеграции, ai ассистент, промпт | AI-интеграции |

| Начальные позиции | стажёр python, стажёр qa, junior, без опыта | Стажировки |

Общие фильтры поиска там, где источник их поддерживает: удалённая работа; опыт «без опыта» и «1–3 года»; регионы Россия и Казахстан отдельными запросами; за последние сутки. Точные названия параметров фиксируются при реализации адаптера.

Запрос по уровню применяется только как фильтр выдачи источника. Вакансия не исключается из-за названия должности: решение принимают правила и фильтры конвейера.

## 7. Чек-лист проверки источников

Выполняется командой проверки источников на шаге A3 с рабочего компьютера и повторяется с сервера на шаге 0.3 перед развёртыванием. Проверка не блокирует разработку: источник, не прошедший её, получает режим `waiting` или `disabled`, остальные подключаются. Результаты вносятся в этот документ.

| № | Проверка | Критерий успеха |
|---|----------|-----------------|
| 1 | Открывается ли t.me/s для каждого из 19 каналов | Страница отдаёт посты без входа |
| 2 | Сколько постов на странице и как запрашиваются более старые | Определён способ догрузки |
| 3 | Работает ли RSS поиска hh.ru с сервера | Лента отдаёт записи, фильтры удалёнки и опыта действуют |
| 4 | Есть ли такая же лента у hh.kz | Да или нет |
| 5 | Условия использования RSS hh и страниц t.me/s | Нет прямого запрета на автоматическое чтение |
| 6 | Хабр Карьера: условия API, работоспособность RSS | Выбран способ или источник отложен |
| 7 | Работа России: доступность API с сервера | Ответ получен, есть признак удалённой работы |
| 8 | SuperJob: возможность регистрации приложения | Ключ получен или источник отложен |
| 9 | Статус заявки на приложение hh | Заявка подана |
| 10 | Замер объёма: сколько новых записей в сутки даёт каждый источник | Выполняется в начальный период эксплуатации по данным `fetch_runs` (шаг C4). Разработку не задерживает |

Пункт 10 нужен для расчёта суточного лимита LLM (ARCHITECTURE.md, вопрос Q8).

## 8. Контроль состояния источников

Контроль источников разделён на три механизма, которые не дублируют друг друга:

| Механизм | Содержание | Раздел | Шаг плана |
|----------|-----------|--------|-----------|
| Оперативное состояние | Ошибки, повторы, деградация, отключение при запрете, оповещения, /status | Этот раздел | A3, входит в MVP |
| Проверка качества каналов | Тихий сбор оценивается, принимается решение о подключении | 4.4 | B5. До него режим меняет владелец в конфигурации |
| Пересмотр активных источников | Раз в 30 дней | 4.5 | C1 |

Общие правила оперативного состояния заданы в ARCHITECTURE.md, раздел 6. Дополнения:

| Событие | Реакция |
|---------|---------|
| Сетевая ошибка, 429, 5xx | Повтор по общим правилам. Курсор не сдвигается, пропущенное добирается следующим запуском |
| 5 сбоев подряд | Источник деградировал: опрос раз в 12 часов, одно оповещение владельцу |
| 403, капча, требование входа | Немедленное отключение до решения владельца (правило R6) |
| Ноль записей 3 запуска подряд при обычной активности источника | Считается сбоем разбора, оповещение владельцу |
| Восстановление после деградации | Обычная частота возвращается, добирается интервал до 14 дней |
| Источник недоступен в момент отчёта | Отчёт выходит по уже собранным данным, источник указан в сводке |
