# IMPLEMENTATION_PLAN.md — план реализации AI Vacancy Hunter

Версия 1.1 от 12.11.2026. Статус: готов к реализации.
Опирается на ARCHITECTURE.md 1.7, TECHNICAL_SPEC.md 1.3, DATABASE_SCHEMA.md 1.5, SOURCES.md 1.6, AGENT_PROMPTS.md 1.0, TEST_PLAN.md 1.1.

Документ задаёт порядок работ. Требования он не повторяет, а ссылается на них.

---

## 1. Правила выполнения

| № | Правило |
|---|---------|
| 1 | Шаги выполняются по порядку. Перед каждым шагом показывается план шага; реализация начинается после слова владельца «согласовано» |
| 2 | Каждый шаг заканчивается работающим состоянием: все тесты проходят, приложение запускается |
| 3 | Тесты шага пишутся в том же шаге (TEST_PLAN.md, раздел 4) |
| 4 | Архитектурные решения не пересматриваются. При противоречии или пробеле в документах работа останавливается, вопрос выносится владельцу |
| 5 | Секреты не попадают в репозиторий, логи и сообщения |
| 6 | Соседний проект на том же сервере не читается, не изменяется и не подключается |
| 7 | Внешняя зависимость, которая недоступна, не блокирует шаг: соответствующий источник или функция отключается в конфигурации, остальное реализуется |
| 8 | Функции MVP не переносятся на более поздние этапы |
| 9 | Каждый шаг — отдельный набор коммитов с понятным описанием |

### 1.2. Принятые имена и команды

Контейнеры: `app`, `db`. Пакеты: `hunter_core`, `vacancy_hunter`. Каталоги: `config/`, `docs/`, `migrations/`, `tests/`, `src/`.

Служебные команды приложения. Создаются на указанном шаге и запускаются как `docker compose exec app python -m vacancy_hunter <команда>`:

| Команда | Назначение | Шаг |
|---------|-----------|-----|
| `check-config` | Проверка файлов конфигурации и наличия секретов | A1 |
| `check-env` | Проверка доступа к базе, Telegram, API LLM, внешнему пульсу | A2, дополняется в A5 |
| `probe-sources` | Пробный запрос к каждому источнику, вывод «доступен» или причина | A3 |
| `collect` | Разовый сбор по одному или всем источникам | A3 |
| `process` | Разовая обработка накопленных записей | A4, дополняется в A5 и A6 |
| `prompt-scenarios` | Прогон сценариев AGENT_PROMPTS.md на реальной модели | A5 |
| `recalc` | Пересчёт оценок | A6 |
| `report` | Разовое формирование отчёта, с ключом пробного режима — без отправки | A7 |
| `cleanup`, `backup` | Очистка и резервная копия | A8 |
| `eval-sample` | Сравнение с размеченной выборкой | A8 |

Общие команды проверки любого шага:

```
docker compose up -d --build
docker compose ps
docker compose exec app pytest
docker compose logs --tail 100 app
```

Сложность: низкая — до одного рабочего сеанса; средняя — два–три; высокая — больше трёх.

## 3. Этап 0 — необходимые проверки

Этап не является отдельной фазой ожидания. Каждая проверка выполняется непосредственно перед тем шагом, которому она нужна.

| Шаг | Когда | Что делается | Готово, когда |
|-----|-------|--------------|---------------|
| 0.1 | Перед A1 | Проверка локального окружения: Git, Docker, Docker Compose, свободное место, доступ к репозиторию | Все программы отвечают версиями; `git push` в пустой репозиторий проходит |
| 0.2 | Параллельно с A1–A4 | Действия владельца: новый бот и токен (к A2), ключ API LLM (к A5), заявка на приложение hh (к B6), адрес внешнего пульса (к A2) | Значения записаны в `.env`. Отсутствие ключа hh ничего не блокирует |
| 0.3 | Перед развёртыванием в A8 | Проверка сервера по ARCHITECTURE.md, раздел 15.1, и повтор `probe-sources` с сервера | Сервер подходит либо выбран другой. Источники, недоступные с сервера, отключены в `sources.yaml` |

Перенесено из прежней редакции этапа 0:

- проверка доступности источников — в шаг A3 (команда `probe-sources`), повтор с сервера — в 0.3;
- сохранение образцов ответов источников — в шаг A3;
- проверка доступа к API LLM — в шаг A5;
- трёхдневный замер числа записей по источникам — в начальный период эксплуатации после A8 (шаг C4). Данные берутся из `fetch_runs`, отдельная работа не требуется.

Недоступный источник получает режим `waiting` или `disabled` и не блокирует остальные.
